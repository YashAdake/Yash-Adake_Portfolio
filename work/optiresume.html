OptiResume

A campus-placement platform on its own domain. It started as an honest ATS scorer that used no AI at all — and that constraint is still the most important decision in the product.

The problem

The resume-checker category is full of tools that quietly do one thing: pipe your CV into a language model and return a confident number. The number moves between runs. The advice invents experience you never had. And the moment you actually need it — the week before a campus drive — you discover the free tier ran out.

Two problems sat underneath that. First, an AI-generated score is not a score; it's a plausible sentence with a digit in it. Second, and bigger: a resume score is not what a candidate actually needs. Getting past the ATS is one gate out of four. They still have an online assessment to sit, an aptitude section to survive, an interview to walk into, and — in India, where most of this happens through campus drives — a fog of unreliable information about which companies are even hiring.

So OptiResume had to be honest about the score and keep going past it.

The decision that shaped everything else

The founding architecture decision — written down as an ADR before a line of scoring code existed — was that the LLM never computes the score. It draws a hard line through the product: anything that must be reproducible, auditable and free is deterministic Python; the model is only invited in for work that is genuinely semantic.

That single boundary is why the rest of the system is affordable, testable, and defensible when a user asks "why did I get 68?" — a question no wrapper around a chat completion can answer.

Decision 01

Rules score. The model writes.

Parseability, section detection, keyword coverage, skill matching, formatting hazards and contact hygiene are 27 explicit rules with explicit weights. They run offline, cost nothing, and produce the same number twice — so the score can be explained line by line and regression-tested like any other pure function.

The LLM handles only what rules genuinely cannot: rewriting a bullet into STAR form using the candidate's own facts, drafting a cover letter, and tailoring a resume to a specific job description.

Decision 02

Never invent experience

Every generative prompt is grounded: the model may only re-say what the candidate already claims. It may sharpen a weak bullet, quantify a vague one, or map it to the recruiter's vocabulary — it may not add a technology, a title, or a result that isn't in the source.

This is the difference between a tool a candidate can walk into an interview behind, and one that gets them caught.

Decision 03

The whole product works signed out — up to a point

An anonymous visitor can run the free rule-based check and see a real score, because the rules are local and cost nothing to run. Using the AI features requires an account, because they cost money per call. Taste before signup; account before spend.

One chokepoint for every AI call

Every LLM call in the product goes through a single gateway module. Not "most" calls — every one. That was a deliberate architectural constraint, because the moment a second code path can reach the provider directly, all of the following stop being guarantees and start being hopes.

  • Prompt-hash caching. Identical work is never paid for twice. The cache key binds to the effective model and sampling parameters, so switching models is a cache miss rather than seven days of stale output from the old one — a subtlety that only showed up during an audit.
  • In-flight deduplication. If two requests for the same work arrive together, the second waits on the first instead of doubling the bill.
  • Layered quotas. A shared daily cap protects the platform; per-user credit quotas protect it from any single user; both are enforced in the same place they're measured.
  • PII redaction before the wire. Personal identifiers are stripped on the way out, and untrusted resume text is wrapped in delimiter tags so the model treats it as data rather than instructions.
  • Per-call cost logging. Every call records its token counts and micro-USD cost, which is what makes the operator console able to answer "what did today cost?" without an invoice.
  • Provider flexibility. A Groq fast-path serves the latency-critical slot while the primary provider handles the rest — swappable because there is exactly one place to swap it.

Built to be trusted with a resume

People upload the single most sensitive document in their professional life. The design answer was to hold as little of it as possible, for as short a time as possible.

Decision 04

Parse and discard

Uploaded files are never stored. The PDF or DOCX is parsed in memory, the extracted text and a content hash are persisted, and the original bytes are dropped. The hash gives deduplication and change detection without keeping the document — so a breach cannot leak a resume that was never written down.

Decision 05

An eight-hour ceiling, not a rolling one

Sessions have an absolute eight-hour lifetime — refreshing extends nothing past that wall. Refresh tokens rotate on every use, and a reused token is treated as theft: the whole family is revoked. The second ADR in the repo exists to explain why the inconvenience is the point.

Decision 06

Verifiable claims, not screenshots

Scores can be turned into a shareable ATS certificate with a QR-verifiable code, so a claim on a profile resolves back to a real record instead of an image anyone could edit.

From resume tool to placement platform

The resume half was the entry point, not the product. What users actually came back for was everything that happens after the resume is good enough — and that half is now the larger one.

  • The Code Century. A curated 100-problem coding track with progress tracking and a verifiable Code Centurion certificate at the end — a finishable goal instead of an infinite problem list.
  • Test series and mock papers. Timed, sectioned tests with scores persisted per attempt, so improvement is measurable rather than remembered.
  • Rapid revision. Compact revision cards for the night before, when nobody is going to read a textbook.
  • A dedicated MBA track. Built separately rather than bolted onto the engineering content, because the syllabus, the scoring conventions and the interview format genuinely differ.
  • A campus-drives directory with a freshness model. Listings carry confidence tiers; stale ones are downgraded automatically and archived after a 90-day grace period, with an admin re-verification queue. Nothing rots quietly into a lie.
  • Programmatic OA-pattern pages for 14 companies, plus an eligibility checker, an application tracker, LinkedIn-profile auditing and cross-checking against the resume, and a share-to-earn credit ledger.
  • An operator console. Activation funnel (signup → verify → analyze → use AI), live LLM spend, audit log, credit requests and a support-query channel — because a solo-run product needs to be observable by the person running it.

What production actually broke

The interesting part of shipping is rarely the launch. Three incidents from this product's first weeks live are worth writing down, because each one changed a rule I now apply everywhere.

Incident · dependencies

A floating dependency took every AI call down

The provider SDK was unpinned. A minor release changed behaviour and every Gemini call in production started failing — with no deploy of mine anywhere near it. Fixed by pinning the exact version and, later, by committing a full constraints lock for the backend image.

Rule learned: a floating dependency is an unscheduled deploy performed by a stranger.

Incident · model aliases

Never gate a model on a -latest alias

The provider repointed a -latest alias to a different model. That model rejected a parameter the previous one accepted, and the calls started returning 400s. The alias had looked like a convenience; it was actually an uncontrolled dependency on someone else's roadmap.

The same batch caught a second edge: the fast provider's token-per-minute window needed max_tokens clamped to it, or bursts were rejected rather than throttled.

Incident · configuration

The API base URL must carry its version prefix

A frontend environment variable set without the /api/v1 suffix produces a build that looks completely healthy and can't reach a single endpoint. It now has a documented invariant and a deploy checklist entry, because the failure mode gives you no useful signal at all — just 404s from a server that is running perfectly.

The product also moved to its own domain mid-life. That meant a full cutover — DNS, mail in both directions, sign-in credentials, CAPTCHA origins, sitemap and search-console re-verification — with permanent redirects left behind on every old URL so nothing that was ever shared goes dead. Deployment runs a dev → pre-prod → prod branch pipeline across both the API host and the frontend host, so nothing reaches production without having been run somewhere else first.

What's next

The work in flight is a large expansion of the preparation half — a substantially bigger question bank, per-topic mastery analytics that recommend one explainable next test rather than a wall of options, a spaced-repetition queue built from the user's own wrong answers, and guided role roadmaps that skip the phases a user can already pass.

All of it is deliberately zero-AI: the founding decision still holds, and none of those features need a language model to work.

Honest note

Everything described on this page is live in production today. The expansion above is built and tested but not yet shipped — it is not counted anywhere on this site until it is. The same rule applies to the resource catalogue behind the roadmaps: where nothing genuinely good and free exists for a step yet, that step ships with an honest blank rather than a padded link.
