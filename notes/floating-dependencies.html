Engineering note · Reliability

A floating dependency is an unscheduled deploy performed by a stranger

Every AI call in OptiResume died in production one morning. Nobody had deployed anything — which is exactly why the outage took so long to find.

What happened

OptiResume’s backend depended on the provider SDK for its LLM calls with an open version range — the default posture of almost every requirements file on the internet. The provider shipped a minor release. Its behaviour changed just enough that every Gemini call in production began failing, and the error surface said nothing about versions. From the outside it looked exactly like an outage I had caused; the investigation kept circling deploys that didn’t exist.

The fix took minutes once the cause was found: pin the exact version. The find took much longer, because the mental model was wrong. I was looking for a change I had made, and there wasn’t one. Someone else had changed my production system, invisibly, by publishing a package.

The reframe

Version ranges are standing permission to deploy to prod

An open range in a lockless environment means: any maintainer of any of my dependencies may change my production behaviour, at a time of their choosing, without telling me. Nobody would grant that permission if it were phrased that way. The requirements file phrases it as >=1.2.

What changed

Pin the SDK, then lock the world

The immediate fix pinned the one SDK. The durable fix committed a full constraints lock for the backend image, so the Docker build resolves every transitive dependency to a known version. Upgrades still happen — but as deliberate, reviewed diffs, on my schedule, with the changelog open.

The subtle part: a lockfile you don’t build from is theatre. The image build had to actually consume the lock, or the pin protects the laptop and not production.

The rule

If you cannot name the exact versions running in production, then you don’t know what’s running in production — you know what was running the last time you looked. Pin what you ship. Treat every upgrade as a deploy, because that is what it is.
